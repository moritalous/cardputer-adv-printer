# 設計メモ

なぜこうなっているか、と、触ると壊れる箇所。
Markdown テンプレートをビルド時に埋め込み、`{{input}}` にキーボード入力を
差し込んで印刷する。USB 印刷まわりの知見はこのファイルに集約してある。

## 全体の流れ

```
contents/print.md  ─┐
contents/images/*  ─┴─→ tools/gen-content.mjs ─→ sketch/content.h ─→ compile → Cardputer ADV

実行時: キーボード入力 → {{input}} 置換 → 1bpp キャンバスへ描画 → USB バルク転送 → M220
```

**`arduino-cli compile` を直接叩かないこと**(生成が走らない)。npm script を使う。
FQBN はオプション付き(`FlashSize=8M,PartitionScheme=default_8MB`)で、
`tools/fqbn.mjs` が唯一の定義場所。

プリンタのアドレス設定ファイルは無い(class 07 で自動検出)。時刻トークンも無い
(Cardputer ADV は RTC 非搭載で、電源断で時刻が消えるため機能ごと不採用)。
画面は入力エディタ専用で、印刷プレビューは持たない。

## 入力まわり

- M5Cardputer の `keysState()` を使う。`word` に文字(Shift 適用済み)、
  `del` / `enter` はフラグで来る
- **esc は独立キーとして存在しない**。左上の `` ` `` キー(キートップ表記 esc)を
  全消去に割り当てている。そのため `` ` `` と `~` は入力できない
- キーリピートは無い(`isChange()` ベース)。del 長押しで連続削除はされない
- 入力は ASCII のみ(ハードウェアキーボードの制約)。テンプレート側は日本語可
- `{{input}}` の置換は**印刷時**に行う(`drawContent()` 内)。印刷が正常終了したら
  入力をクリアして次の客を待つ。失敗時は残す(打ち直しさせない)

## バッテリー表示

編集画面の右上にアイコン+パーセントを出す。`M5Cardputer.Power.getBatteryLevel()` は
Cardputer ADV では **GPIO10 の ADC 実測(分圧比 2.0)を線形に %化**したもの
(M5Unified の `pmic_adc` 経路)。式は `(mv - 3300) * 100 / (4150 - 3350)` で、
分子の基準 3300 と分母の 3350 が食い違っている(M5Unified 側がそう書いてある)。
実質 **3300mV = 0%、4100mV = 100%** で、それ以上はクランプ。電圧ベースなので
負荷で数 % 揺れる。

- **充電中は判別できない**。`isCharging()` に `pmic_adc` のケースが無く `unknown` を返す
- ADC 読みなので毎ループは叩かず 10 秒間隔(`BATT_POLL_MS`)。値が変わった時だけ再描画
- 再描画は `ready && !busy` の時だけ。印刷中は `statusScreen()` が画面を専有しており、
  上書きすると進捗表示が壊れる
- パーセントはアイコンの**下**に置く。プロンプト(`INPUT_PROMPT`)は同じ行に中央寄せで
  出るので、横に並べると長いプロンプトで衝突する

## 1bpp キャンバス

Cardputer ADV に PSRAM は無い(SRAM 512KB)。464×2000 のキャンバスを 16bpp で取ると
1.8MB で確保不能なので 1bpp(116KB)。テキストは 2 値で描かれるため情報の損失は無く、
実行時ディザも不要。

印刷データは `canvas.getBuffer()` の**フレームバッファ直読み**。1bpp スプライトは
1bit/px・58 バイト/行・MSB が左端で、印刷ラスタと同形式。白黒の意味だけ逆
(パレット index 1 = 白、プリンタは bit 1 = 黒)なので、行ごとのビット反転コピーで
送信データになる。

画像は `drawBitmap()` で描く(gen-content が 1bpp パック済みで埋め込む)。
`drawPng()` は 1bpp パレットスプライトで全ピクセルが黒になるため使えない(実機で確認)。

折り返しはスプライト右端(464px)で LovyanGFX 任せ。**`drawContent()` に
`setClipRect` を足さない**(折り返し境界が 464 → 424 に変わり、今は折り返さない
行が折り返して印刷結果が変わる)。折り返し後の行は左マージンに揃わず x=0 から
始まる(既知の制限。現状のテンプレートは折り返さない前提)。

## USB まわり(このプロジェクトの本体)

### Serial/JTAG と OTG ホストは排他

ESP32-S3 の USB PHY は 1 つで、**書き込み用の USB-Serial/JTAG と、プリンタをつなぐ
OTG ホストが排他**。`usb_host_install()` した瞬間から、次の電源入れ直しまで
PC からの書き込みは効かない。

だからスケッチは**起動時にはホストを初期化せず、初回印刷時に初めて初期化**する。
書き込み直後なら何度でも再書き込みできる。`scan`(ディスクリプタビューア)が
結果をシリアルではなく本体画面に表示するのも同じ理由(ホスト開始 = シリアル死)。

### M220 は「ハンドシェイク」するまでジョブを無視する(最重要)

**電源を入れた直後の M220 は、正しいプロトコルのジョブを送っても黙って捨てる。**
プリンタ画面に「受信中」は出るのに何も印刷されない。データも転送も正常なのに、である。

USB プリンタクラスのリクエストを一度でも送ると、以後(プリンタの電源を切るまで)
ジョブが普通に印刷されるようになる。Windows の usbprint.sys はデバイス接続時に
必ず GET_DEVICE_ID を送るので、PC からは「何もしなくても」動く。素の USB ホストを
自作すると、この暗黙の儀式が抜けてハマる。

`usb_printer.cpp` は claim 後に以下を行う(`ensureInited()`):

1. **GET_DEVICE_ID**(class request 0x00)— 応答は使わない。送ること自体に意味がある
2. **GET_PORT_STATUS**(class request 0x01)
3. **bulk IN の常時読み捨て**開始 — M220 はジョブ後にステータス(実測で `1A 0F 0C`)を
   送ってくる。誰も読まないと IN パイプが詰まる

どれが必要最小かは切り分けていない(3 点セットで実機確認済み)。**削らないこと。**

ちなみに M220 の IEEE1284 ID は
`MFG: ;CMD:XPP,XL;MDL:M220;CLS:PRINTER;DES:LABEL PRINTER;`。

### ラスタは単一ブロックで送る(分割すると継ぎ目が入る)

`GS v 0` ブロックを複数に分割して送ると、**プリンタがブロック間で紙送りを入れ、
印刷物に白い継ぎ目が入る**(実機で確認)。512 行の単一ブロックは USB でも問題なく
印刷できるので、**ジョブ全体を 1 ブロック**で送る(`MAX_BLOCK_ROWS = MAX_CANVAS_H`)。

開発中に「240 行以下に分割したら直った」ように見えた局面があったが、それは
同時に入れたハンドシェイクが効いていただけ(2 変数を同時に変えた凡ミス)。
phomemo-tools に「M110/M220 系は 240 行/ブロック」とあるのは公式ドライバの
挙動であって、ファームの上限ではない。**分割を「修正」として再導入しないこと。**

### プリンタの判別は class 07 限定

bulk OUT を持つ任意のデバイスにマッチさせると、USB メモリに印刷ジョブを
流し込みかねない。**インターフェースクラス 0x07(プリンタ)だけ** claim する。
class 07 でないデバイスは画面に `not a printer (class XX)` と出る。

### 切断処理・ドレイン待ちは無い

印刷後も USB 接続は**つないだまま**にする(2 回目以降の印刷が即座に始まる)。
Bluetooth(SPP)でこの種のプリンタを使う場合は「印字が終わる前に切断すると
ジョブが中断する」ためドレイン待ちが必要になるが、USB 版は切断自体をしないので
その問題が存在しない。

### プロトコル

Phomemo 系。同じバイト列で Bluetooth(SPP)経由でも印刷できることを実機確認済み。

```
ヘッダ: 1B 4E 0D 05 / 1B 4E 04 0A / 1F 11 0B(連続紙モード)
ラスタ: 1D 76 30 00 xL xH yL yH + データ(58 バイト/行)
フッタ: 1F F0 05 00 / 1F F0 03 00
```

## 触ると壊れる箇所まとめ

- `ensureInited()` のハンドシェイク 3 点セットを削らない(まっさらなプリンタが無反応になる)
- ラスタを複数ブロックに分割しない(継ぎ目が入る)。`MAX_BLOCK_ROWS = MAX_CANVAS_H` を維持
- `drawContent()` に `setClipRect` を足さない(折り返し境界が変わる)
- 画像は `drawBitmap`。`drawPng` に戻さない(1bpp パレットで全黒になる)
- `CONTENT_W = 384` は `sketch/sketch.ino` と `tools/gen-content.mjs` の両方にある。一致させる
- `println("")` は行送りの実測(LovyanGFX に行高取得 API が無い)。無意味に見えるが必要
- FQBN の `FlashSize=8M,PartitionScheme=default_8MB` を外さない(既定は 4MB/1.2MB app 想定で、
  日本語フォント+画像で溢れる)。定義は `tools/fqbn.mjs` だけ
- キャンバスは 1bpp 前提。フレームバッファ直読み(反転コピー)と生成画像の純黒白が
  この前提に依存している

## ハマった点の記録

### USB Serial/JTAG は DTR が立っていないと応答が届かない

シリアルでデバイスと対話するツールを書くときは、ポートを開いた後
`dtr: true, rts: false` を設定すること。DTR を落とすと「端末不在」扱いで
デバイス側の送信が捨てられる。DTR/RTS の定常状態はリセットを誘発しない
(リセットは特定のトグルシーケンス)。

### M5Unified は Serial を初期化しない

`cfg.serial_baudrate` を設定しないと `Serial.begin()` が呼ばれない。
現在のスケッチはシリアルを使わないので設定していないが、シリアル対話機能を
足すときは思い出すこと。

### ポート検出は VID 0x303A

Cardputer ADV に USB-UART ブリッジチップは無く、ESP32-S3 自身が
Espressif VID `0x303A` / PID `0x1001`(USB Serial/JTAG)で列挙される(`tools/port.mjs`)。

### 「ポートが見えない」の 9 割はホストモード

一度でも印刷(またはスキャン)すると PHY が OTG に取られ、PC につないでも
何も列挙されない。**ケーブルを抜いた状態で電源スイッチを入れ直す**と直る。
PC につないだままスイッチを切っても USB 給電で動き続けるので注意。

## 診断ツール

- `scan/scan.ino` — USB ディスクリプタビューア(`npm run scan` で書き込み)。
  つないだデバイスの VID/PID・クラス・エンドポイントを画面に表示する

印刷が無反応になったときの切り分けの勘所: ①プリンタの電源を入れ直したか
(ハンドシェイク状態が消える)→ そのまま再印刷で直るか、② `scan` で class 07 と
bulk OUT が見えているか、③プリンタ画面に「受信中」が出るか(出るならデータは
届いており、ジョブの中身かハンドシェイクの問題)。
